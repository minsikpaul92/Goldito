## FB-1. 케어 줄 입력칸 라벨 (런북 §2 단계 1 — 할 일 만들기)

## FB-3. 날짜 · 시간 UI를 전부 같은 방식으로

- **원하는 것:** (사진 1)
  - **날짜를 누르면 달력**, **시간을 누르면 시계**가 뜸.
  - **− / + 는 그대로 유지** — 날짜는 **하루씩**, 시간은 **15분씩**.
  - 이 규칙을 **DESIGN.md에 정리**하고 **모든 UI에 같은 걸 적용**.
- **현재 상태 (확인):**
  - 날짜 탭 → 달력(`DayPickerSheet`)은 **Book care · 문의 시트(`HandoffPicker`)에만** 있음 (어제 추가).
  - **시간**은 `Stepper`(− +)만 — 탭해도 아무 일 없음. (시계 모양 `TimePickerSheet`는 케어 할 일 시간에만 있음.)
  - `HandoffChangeSheet`(사진 1) · `MeetGreetSheet` · `ScheduleSheet`(시터 스케줄) · `CareLineBuilder`(Several times)는 `Stepper`만 씀 → **서로 다름**.
- **DESIGN.md:** §7.10 "Dates and times"를 새로 적어 두었습니다 (규칙 · 컴포넌트 · 적용 대상 목록).
- **아이디어:**
  1. 공용 컴포넌트 `DateField` · `TimeField`를 만든다 — `[−] 값(탭하면 시트) [+]` 한 줄. `DateField`는 `DayPickerSheet`, `TimeField`는 `TimePickerSheet`(휠, 15분 단위로 스냅 옵션)를 연다. 속성: `min`/`max`, `step`, 에러 문구, `testID`.
  2. 적용 순서(작은 것부터): `HandoffChangeSheet` → `HandoffPicker`의 시간 → `MeetGreetSheet` → `ScheduleSheet` → `CareLineBuilder`(Several times) → 그 밖에 `Stepper`를 쓰는 곳 (`git grep "<Stepper"`).
  3. `Stepper`는 숫자/횟수용(마리 수 등)으로만 남기고 날짜·시간에는 안 씀.
  4. 달력 시트: 선택 가능한 가장 이른 날(min) 이전은 비활성, 월 이동. 시계 시트: 시 · 분 · AM/PM 휠 (이미 있음).
- **확인:** `UX-1`을 "날짜 → 달력, 시간 → 시계"로 넓히고, 화면마다 한 줄씩 (BOOK · 변경 시트 · 문의 · M&G · 스케줄).

## FB-5. 시간 변경 시트 — 오갈 때 값이 날아감 · Close · 최종 Send

- **본 것:** (사진 1) Drop-off 와 Pick-up 버튼을 누르면 **고치던 값이 저장되지 않고** 기존 값으로 돌아감. Close 를 누르면 그냥 닫혀야 하는데 이상하게 동작함 ("완전 버그").
- **원하는 것:**
  1. 시간을 바꾸면 **임시 저장** → Drop-off ↔ Pick-up 을 **자유롭게 오가도 각각 유지**.
  2. **Send to Chloe**를 누르면 **그때 최종 저장 + 전송** (바뀐 것 전부).
  3. 고치다가 **Close** 를 누르면 **그냥 닫힘** (저장도 전송도 없음, 다음에 열면 서버의 현재 값으로 시작).
- **원인 (코드에서 확인):** `frontend/components/HandoffChangeSheet.tsx` — 상태가 `draft` 하나이고, 종류를 바꿀 때 `setDraft(draftFor(booking, kind))`로 **통째로 새로 만듦** → 고치던 값이 사라짐. 전송도 한 번에 한 종류(`onSubmit({kind, at, place})`)만.
- **아이디어:**
  1. 상태를 `{ drop_off: Draft, pick_up: Draft }` 두 개로 들고, 종류 버튼은 **보이는 쪽만 바꿈** (값은 각각 유지).
  2. "바뀐 종류" = 서버 값과 다른 것. **Send** 때 바뀐 종류마다 `propose_handoff`를 순서대로 호출 (둘 다 바뀌면 2번). 하나가 실패하면 어디까지 보냈는지 보여 주고 나머지 재시도.
  3. 두 종류 중 하나라도 규칙 위반(과거 시각, "Somewhere else"인데 장소 없음)이면 Send 비활성 + 어느 쪽이 문제인지 표시 (탭에 ⚠️).
  4. Close/배경 탭 = `onClose`만 호출. 시트를 `key`로 다시 열면 초기화 (지금도 그렇게 하고 있는지 확인 — 닫은 뒤 다시 열었을 때 이전 값이 남는다면 그게 "Close 버그").
  5. 이미 끝난 인수인계는 목록에서 제외 → **FB-6**.
- **확인:** `HANDOFF-x` 시나리오: ① 드롭오프 시간 바꿈 → 픽업 탭 → 드롭오프 탭 → 값 유지 ② Send → 두 요청 전송 ③ Close → 아무 요청 없음.
- **재현 확인 필요:** "Close 가 이상함"이 구체적으로 (a) 안 닫힘 (b) 닫혔는데 다음에 값이 남음 (c) 닫히면서 전송됨 중 무엇인지.

## FB-6. "That handoff already happened."

- **본 것:** (사진 4) 오른쪽 요청을 보냈더니 이 문구가 아래에 빨간 글씨로 나옴. 예약 상세의 Drop-off 줄은 **"✓ Received 1:37 AM"** — 이미 받은 인수인계.

- **아이디어:**
  1. 시트의 종류 버튼에서 **완료된 인수인계는 숨기거나 비활성** ("Drop-off · done ✓"), 기본 선택은 아직 안 끝난 것. 둘 다 끝났으면 "Change time or place" 버튼 자체를 숨김.

- **확인:** `HANDOFF-4` — Received 이후 Drop-off 변경이 불가능하다는 걸 UI가 먼저 막음.

## FB-7. Finish booking → "Can't open checkout — This sitter doesn't offer that service."  ⛔ 막힘

- **본 것:** (사진 5) 시터 쪽은 **Confirmed**인데 오너가 **Finish booking**을 누르면 체크아웃이 안 열림.
- **원인 (호스팅 DB에서 확인):** `sitter_rates` 테이블이 **비어 있음 (0행)**. `quote_booking`은 요금표가 없으면 `service_not_offered`를 던지고, 화면은 그걸 "doesn't offer that service"로 번역. (`services`에는 `boarding`이 있음 — 즉 거짓 오류 문구이기도 함.) 데모 시드(`seed_demo.py`)가 요금표를 안 넣었고, 시터가 요금을 정하는 화면도 없음.
- **영향:** 체크아웃 불가 → 결제 → Received → 돌봄 → Returned → 리뷰 · Life Record **전부 막힘**. 문의 AI도 가격 문장을 못 만듦 (견적 없음).
- **임시 조치 (2026-10-08, 호스팅 DB에 직접 한 행):** Chloe `sitter_rates` = 보딩 1박 **$55** · 추가 반려동물 +50% · 공휴일 +25% (CAD). 하우스시팅 · 데이케어 요금은 비움 — DB 규칙상 **시터가 켠 서비스(지금은 보딩만)**의 요금만 넣을 수 있음. 확인: 보딩 3박 · 2마리 · Thanksgiving → `quote_booking` = **$268.13 CAD** (문서 예시와 같음). 요금 입력 화면은 이 단계에서 만들지 않음. `reset_demo.py`를 만들 때 이 행을 보장해야 함.
- **아이디어:**
  1. **당장:** 요금표 시드 — 데모 시터 Chloe에 `sitter_rates` 한 행(boarding 1박 $55, house sitting 1박 $65, 추가 반려동물 +50%, 공휴일 +15% — 문서의 견적 예시 $268.13이 나오는 값 [phase-03c.md] 확인해서 그대로). `seed_demo.py`에 포함하고 FB-10의 리셋에서도 보장.
  2. **문구:** 요금표가 없을 때는 "Chloe hasn't set her prices yet" 같은 **진짜 이유**로 (오너) + 시터에게 "Set your prices" 알림. `service_not_offered`는 진짜로 서비스를 안 하는 경우에만.
  3. **중기:** 시터 프로필에 **Prices**(보딩 · 하우스시팅 1박, 추가 펫 %, 공휴일 %) 입력칸 — 요금이 없으면 시터가 "요청 Accept" 전에 안내. (시터 UI 개편 FB-11과 묶어서)
- **확인:** `BOOK-5`(견적 → 동의서 → 결제) 를 실제 DB에서 처음으로 통과.

## FB-9. Returned 가 검증 없이 바로 처리됨

- **본 것:** 시터가 **Returned**를 누르면 **바로** 처리됨. 확인 단계가 없음.
- **원인:** 시터 예약 상세의 버튼이 `completeHandoff(booking.id, "pick_up")`을 바로 부름. 서버 `complete_handoff`는 드롭오프가 완료됐는지만 검사하고, 드롭오프와 달리 **픽업은 시각 제한이 없음** (아직 이른데도 가능).
- **아이디어 (작은 것부터):**
  1. **확인 시트**: "Max & Mochi are going home with Robert. This can't be undone." + 아직 안 한 오늘 할 일 수 · 알림장을 아직 안 보냈다면 알림("Send today's note first?") + **Confirm Returned** / Cancel.
  2. **시각 가드**: 합의된 픽업 시각의 2시간 전부터만 활성 (Received와 같은 규칙). 서버에도 `handoff_too_early`를 픽업에 추가 (9c 같은 소규모 마이그레이션).
  3. **오너 확인(선택)**: 오너 화면에 "Max is home — Confirm received" 한 번 (분쟁 방지, P1).
  4. **06B**(Pet Transit): 귀가 **사진 체크**(`return` — 펫이 보이는지 · 크레이트/벨트)를 Returned의 조건으로 붙이면 이것이 진짜 "검증". 06B.5 · 06B.6에 연결 (계획에 이미 있음).
- **확인:** `HANDOFF-5` — Returned 전에 확인 시트, 너무 이른 시각이면 비활성, 확인 후에만 처리.
