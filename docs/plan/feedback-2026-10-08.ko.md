## FB-1. 케어 줄 입력칸 라벨 ("Write a care checklist" 화면 — `CareLineBuilder`)

- **본 것:** 라벨이 `Meals — what to give or do (empty = the hint)` 처럼 길게 한 줄로 붙어 있음.
- **원하는 것:** 엠대시(`—`)를 지우고, `what to give or do (empty = the hint)` 부분은 **작은 글씨 · 연한 회색**. **위치는 그대로**.
- **원인:** `frontend/components/CareLineBuilder.tsx:130` — 라벨 문자열 하나에 전부 들어 있음 (`TextField`의 `label`).
- **아이디어:**
  1. `TextField`에 선택 속성 `hint`를 추가 — 라벨(굵게, 지금 그대로) 오른쪽/아래에 `fontSize.small` + `textMuted`에 투명도를 줘서 한 단계 더 연하게 보이는 보조 문구로 그림. 위치는 라벨 줄 안에 이어서(같은 줄, 라벨 뒤)로 두면 "위치 그대로".
  2. `CareLineBuilder`는 `label={kindMeta(kind).label}` + `hint="what to give or do (empty = the hint)"`로 호출.
  3. DESIGN.md §6 `TextField` 행에 "라벨 + 작은 연회색 hint" 규칙 추가 (이미 적어 둠).
- **위치 정정 (리뷰):** 이 라벨은 Care tasks → Add task가 아니라 펫 화면의 **"Write a care checklist"**(케어 요청서) 화면에 있음.
- **확인:** `FLOW-12` · 다른 `TextField`의 모양은 안 변함.

## FB-2. 요청이 상대 화면에 실시간으로 안 뜸

- **본 것:** "요청을 보냈는데 바로 실시간으로 안 뜸". (어떤 요청인지 사진에는 없음 — **예약 요청**(런북 §2 단계 2)이나 **케어 요청서**일 가능성. 아래는 둘 다 적습니다. 확인 부탁: 어느 쪽이었는지.)
- **원인 (코드에서 확인):**
  - 시터 **Bookings** 탭은 화면에 들어올 때(`useFocusEffect`) 한 번만 목록을 읽음. 새 요청이 와도 다시 읽지 않음.
  - 시터 **Home**의 "📝 Care request … tap to answer" 줄도 `listPendingChangeRequests()`를 포커스 때만 읽음.
  - 알림(`booking_requested` · `care_request`)은 Realtime으로 즉시 도착해 토스트/벨은 뜨지만, **화면 데이터를 다시 읽으라는 신호로는 쓰이지 않음** (`NotificationsProvider`는 feed · diary · inbox revision만 올림).
- **아이디어:**
  1. `NotificationsProvider`에 `bookingsRevision` · `careRevision`(또는 알림 `type` 목록을 받는 `useNoticeRefresh(types, reload)` 훅)을 추가 — 알림이 INSERT될 때 해당 타입이면 숫자를 올림.
  2. 시터 Bookings · Home · 오너 Bookings · 펫 화면이 그 값이 바뀌면 조용히 다시 읽음 (로딩 화면 없이).
  3. 대상 타입: `booking_requested` · `booking_confirmed` · `booking_declined` · `handoff_*` · `meet_greet_*` · `care_request*` · `inquiry_*` · `review_*` · `life_record_updated`.
  4. 안전망: 화면이 보이는 동안 30초마다 한 번 읽기 (알림이 늦거나 놓쳤을 때).
- **확인:** `FLOW-1` (오너가 요청 → 시터 화면이 새로고침 없이 갱신), 반대 방향 `FLOW-2` (시터 Accept → 오너 화면 갱신). *(LIVE-x는 §3.6에서 다른 뜻으로 이미 쓰이므로 쓰지 않음.)*
- **같이 볼 것 (리뷰):** 오너 Diary는 `report_sent`, 끝난 예약의 Life Record 카드는 `life_record_updated`가 와도 갱신 안 됨 — 같은 `useNoticeRefresh`로.

## FB-3. 날짜 · 시간 UI를 전부 같은 방식으로

- **원하는 것:** (사진 1)
  - **날짜를 누르면 달력**, **시간을 누르면 시계**가 뜸.
  - **− / + 는 그대로 유지** — 날짜는 **하루씩**, 시간은 **15분씩**.
  - 이 규칙을 **DESIGN.md에 정리**하고 **모든 UI에 같은 걸 적용**.
- **현재 상태 (확인):**
  - 날짜 탭 → 달력(`DayPickerSheet`)은 **Book care · 문의 시트(`HandoffPicker`)에만** 있음 (어제 추가).
  - **시간**은 `Stepper`(− +)만 — 탭해도 아무 일 없음. (시계 모양 `TimePickerSheet`는 케어 할 일 시간에만 있음.)
  - `HandoffChangeSheet`(사진 1) · `MeetGreetSheet` · `ScheduleSheet`(시터 스케줄) · `CareLineBuilder`(Several times)는 `Stepper`만 씀 → **서로 다름**.
- **DESIGN.md:** §7.10 "Dates and times"를 새로 적어 두었습니다 (규칙 · 컴포넌트 · 적용 대상 목록).
- **아이디어:**
  1. 공용 컴포넌트 `DateField` · `TimeField`를 만든다 — `[−] 값(탭하면 시트) [+]` 한 줄. `DateField`는 `DayPickerSheet`, `TimeField`는 `TimePickerSheet`(휠, 15분 단위로 스냅 옵션)를 연다. 속성: `min`/`max`, `step`, 에러 문구, `testID`.
  2. 적용 순서(작은 것부터): `HandoffChangeSheet` → `HandoffPicker`의 시간 → `MeetGreetSheet` → `ScheduleSheet` → `CareLineBuilder`(Several times) → 그 밖에 `Stepper`를 쓰는 곳 (`git grep "<Stepper"`).
  3. `Stepper`는 숫자/횟수용(마리 수 등)으로만 남기고 날짜·시간에는 안 씀.
  4. 달력 시트: 선택 가능한 가장 이른 날(min) 이전은 비활성, 월 이동. 시계 시트: 시 · 분 · AM/PM 휠 (이미 있음).
- **확인:** `FLOW-10` (화면마다: Book care · 변경 시트 · 문의 · M&G · 스케줄 · 케어).

## FB-4. 예약 상세에서 사람이 누구인지 표시

- **본 것:** (사진 2) 오너의 예약 상세 맨 위 카드에 **"Chloe"** 라고만 있어서 **시터인지 알 수 없음**.

- **원인 (리뷰 정정):** 헤더의 알약은 `frontend/components/HeaderActions.tsx`(21~22줄)에 있고 **개발 빌드(`__DEV__`)에서만** 그려짐(역할 전환용 개발 도구) → 운영 빌드에는 복사할 원본이 없음. 그래서 `RoleBadge`는 **새 컴포넌트**로 만들고(모양은 그 알약과 같게: 초록 배경 · 둥근 모서리 · 작은 굵은 글씨, 토큰은 DESIGN.md), 헤더의 개발용 알약도 이 컴포넌트를 쓰게 바꾼다.

  3. DESIGN.md §6 컴포넌트 표에 `RoleBadge` 행 추가 (이미 적어 둠).
- **확인:** `FLOW-11`.

## FB-5. 시간 변경 시트 — 오갈 때 값이 날아감 · Close · 최종 Send

- **본 것:** (사진 1) Drop-off 와 Pick-up 버튼을 누르면 **고치던 값이 저장되지 않고** 기존 값으로 돌아감. Close 를 누르면 그냥 닫혀야 하는데 이상하게 동작함 ("완전 버그").
- **원하는 것:**
  1. 시간을 바꾸면 **임시 저장** → Drop-off ↔ Pick-up 을 **자유롭게 오가도 각각 유지**.
  2. **Send to Chloe**를 누르면 **그때 최종 저장 + 전송** (바뀐 것 전부).
  3. 고치다가 **Close** 를 누르면 **그냥 닫힘** (저장도 전송도 없음, 다음에 열면 서버의 현재 값으로 시작).
- **원인 (코드에서 확인):** `frontend/components/HandoffChangeSheet.tsx` — 상태가 `draft` 하나이고, 종류를 바꿀 때 `setDraft(draftFor(booking, kind))`로 **통째로 새로 만듦** → 고치던 값이 사라짐. 전송도 한 번에 한 종류(`onSubmit({kind, at, place})`)만.
- **아이디어:**
  1. 상태를 `{ drop_off: Draft, pick_up: Draft }` 두 개로 들고, 종류 버튼은 **보이는 쪽만 바꿈** (값은 각각 유지).
  2. "바뀐 종류" = 서버 값과 다른 것. **Send** 때 바뀐 종류마다 `propose_handoff`를 순서대로 호출 (둘 다 바뀌면 2번). 하나가 실패하면 어디까지 보냈는지 보여 주고 나머지 재시도.
  3. 두 종류 중 하나라도 규칙 위반(과거 시각, "Somewhere else"인데 장소 없음)이면 Send 비활성 + 어느 쪽이 문제인지 표시 (탭에 ⚠️).
  4. Close/배경 탭 = `onClose`만 호출. 시트를 `key`로 다시 열면 초기화 (지금도 그렇게 하고 있는지 확인 — 닫은 뒤 다시 열었을 때 이전 값이 남는다면 그게 "Close 버그").
  5. 이미 끝난 인수인계는 목록에서 제외 → **FB-6**.
- **원인 보충 (리뷰):** `app/owner/bookings/[bookingId]/index.tsx`의 `send`(179~185줄)가 **RPC를 부르기 전에 시트를 닫음** → 실패하면 입력하던 값이 사라지고 오류는 페이지에 뜸. 고칠 때: 시트는 성공한 뒤에 닫고, 오류는 시트 안에(FB-6 아이디어 2와 같음).
- **확인:** `FLOW-7` · `FLOW-8`: ① 드롭오프 시간 바꿈 → 픽업 탭 → 드롭오프 탭 → 값 유지 ② Send → 두 요청 전송 ③ Close → 아무 요청 없음.
- **재현 확인 필요:** "Close 가 이상함"이 구체적으로 (a) 안 닫힘 (b) 닫혔는데 다음에 값이 남음 (c) 닫히면서 전송됨 중 무엇인지.

## FB-16 · FB-17. 직접 추가하는 칩 — 취소 · 삭제 (10/09, 민식) — ✅ 수정됨

- **수정:** "+ Add" 버튼과 따로 열리는 입력칸을 없애고, 늘 보이는 **"Anything to add? One short line at a time"** 입력칸 + Add(또는 Enter) 하나로 합침(FB-18). 열고 닫는 상태가 없으니 취소 = 칸을 비우기. 직접 추가한 칩에만 **×**(지우기), AI가 제안한 칩은 지금처럼 끄기만(D38).

- **본 것:** "+ Add"를 누르면 입력칸이 열리는데 닫을 방법이 없음. 추가한 칩은 켜고 끄기만 되고 지워지지 않음.
- **생각:** 입력칸 옆에 **Cancel**(입력 내용 버림). 직접 추가한 칩에만 작은 **×**(지우기) — AI가 제안한 칩은 지금처럼 켜고 끄기만(D38: 지우는 대신 끔).

## FB-18. "Anything to add?" — 짧은 줄 여러 개 (10/09, 민식) — ✅ 수정됨 (결정: (b))

- **결정 (민식):** (b) 각 줄을 직접 추가한 칩으로. **수정:** 줄 하나(최대 40자) = 칩 하나, 입력 후 칸이 비워져 다음 줄을 바로 씀. 알림장 요청에 따로 가던 `sitter_note`는 이제 비움(`null`) — 시터의 말은 칩으로 가고 **맨 앞 순서**(8개 제한에서도 우선). 백엔드는 그대로.

- **본 것:** 메모가 한 칸(최대 200자)이라 여러 가지를 쓰려면 한 줄로 이어 써야 함.
- **생각:** 한 줄씩 입력 → **+ another line**으로 줄 추가, 각 줄 옆 ×. 보낼 때는 줄을 합쳐 `sitter_note` 하나로(합계 200자 제한 유지, D38 "선택 입력"). 백엔드 변경 없음. 또는 각 줄을 직접 추가한 칩으로 만드는 안 — FB-16/17과 합치면 입력 방식이 하나로 줄어듦 (결정 필요).
